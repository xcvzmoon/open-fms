# Security

## The download rule

Only files with PostgreSQL status `clean` may be streamed.

This is a hard rule. Signed URLs cannot be revoked after a file leaves `clean`, so v1 proxies every download and re-checks state per request.

## Auth

- Better Auth handles sessions, passwords, API keys, permissions, and per-key rate limits
- `caller_credentials` binds Better Auth key IDs to CIDRs, MIME types, size, expiry, and credential lifecycle; FMS also enforces caller-wide rate limits
- Administrator routes require a verified browser session and trusted mutation origin
- Suspended and disabled callers cannot access existing resources
- Setup codes are HMAC hashes with a versioned pepper

## API key permissions

Issue keys through `POST /api/v1/callers/{id}/keys` with a verified administrator session and trusted origin. Supply `permissions` as resource/action grants. The only supported grants are `uploads: ["write"]` and `files: ["read"]`; at least one is required. Unknown resources, unsupported actions, empty arrays, and the obsolete `scopes` field are rejected.

```json
{
  "label": "file reader",
  "kind": "standard",
  "permissions": { "files": ["read"] },
  "allowedCidrs": [],
  "allowedTypes": [],
  "maxFileSizeBytes": null,
  "rateLimitPerSec": null
}
```

Clients send the returned secret in `x-api-key`. Upload mutations require `uploads/write`. Upload GET/HEAD and file routes require `files/read`. Better Auth verifies the key and its required grants once per request. A missing, expired, revoked, or insufficiently permitted key returns HTTP 401 `AUTH_REQUIRED`. FMS policy denials, including CIDR and MIME restrictions, return HTTP 403. API keys cannot access administrator or signup routes or impersonate browser sessions.

Rotation preserves the exact stored grants and FMS policy, disables the old key, and records an audit event. Missing or malformed grants prevent rotation with `CREDENTIAL_PERMISSIONS_INVALID`; administrators must issue a new key with explicit permissions. No default grants are inferred.

### Upgrading existing credentials

Keys issued before native permissions have no stored grants and will fail resource requests after this release. Plan a maintenance window and replacement distribution before deployment. Inventory affected callers and their intended grants before applying the schema change; never export plaintext secrets.

Stop old API instances, apply the normal database migrations, and start the complete new release. The schema migration drops `caller_credentials.scopes`; it does not copy legacy grants or change existing key permissions. Never run old and new API versions together during this cutover.

Administrators must issue replacement keys with explicit permissions, deliver them securely, update clients, and revoke superseded keys. An unconfigured old key cannot be rotated to recover its permissions. Expect interrupted service until clients have replacements. Do not roll back only the application after dropping the scopes column; restore a coordinated database/application backup if rollback is required.

## Isolation

Each request has one `caller_id`. Queries filter by tenant. Admin routes are the only cross-tenant paths.

## Not in v1

- Presigned GET downloads
- Automatic status repair from reconcile
- Enabling storage backends before compatibility tests

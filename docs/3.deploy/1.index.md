# Deploy

Open FMS is a Nitro application. Build it and deploy the `.output` folder.

## Build

```bash
vp run build
```

## Runtime requirements

- PostgreSQL reachable through `DB_URL`
- Migrations applied before traffic
- Storage credentials when uploads/downloads are used
- Stable `BETTER_AUTH_SECRET` and `BETTER_AUTH_URL`
- Explicit SMTP configuration with verified TLS in production
- A separate scan worker and reachable ClamAV daemon

## Process model

| Process         | Role                   |
| --------------- | ---------------------- |
| API             | Nitro HTTP server      |
| Scan worker     | Long-running scan loop |
| Scheduled tasks | Sweepers and canary    |

Scanning is intentionally a separate process from the API.

## Health probes

- Liveness: `/healthz`
- Readiness: `/readyz`

## Migrations

Never run migrations from the API boot path. Use CI or a one-shot job.

```bash
vp run --filter "@open-fms/database" migrate
```

## Storage compatibility

Before enabling a real backend, validate presigned PUT, copy, multipart, range reads, and ETag behavior with the integration suite in `@open-fms/storage`:

```bash
docker compose -f compose.storage.yaml up -d --wait
STORAGE_TEST_ENDPOINT=http://127.0.0.1:9000 \
STORAGE_TEST_ACCESS_KEY_ID=rustfsadmin \
STORAGE_TEST_SECRET_ACCESS_KEY=rustfsadmin \
  vp run test
```

Point `STORAGE_TEST_*` at the candidate backend (RustFS, MinIO, or AWS S3) and create the quarantine, clean, and forensic buckets first.

## Onboarding and policy changes

Create the initial account using `auth:bootstrap-admin create <email> <name>` from `apps/api`, passing its password on stdin. Verify the emailed link, then run `auth:bootstrap-admin promote <user-id>`. Configure signup domains through the administrator API before inviting callers.

The ownership migration requires each existing caller to have an explicit verified Better Auth owner. Existing caller rows must be mapped before applying the NOT NULL ownership constraint; migrations deliberately cannot infer that mapping from UUIDs. Back up the database and resolve ownership in a controlled maintenance window. Fresh installations migrate directly. Old API keys need a matching FMS policy record; unpaired keys are denied. Direct upload sessions and upload passes have been removed.

Retention starts at successful upload completion. Due files are tombstoned before physical deletion; quota is released only after all configured bucket copies are deleted. Failed deletion is retried. Legal holds and future retention dates block deletion. PostgreSQL readiness does not certify object storage; inspect the separately reported storage canary, including skipped checks.
